# ADR-010 ADR-010 双桥派发：CLI 会话优先，子代理回退，一轮一会话

- 日期: 2026-10-27
- 状态: 已接受

## 背景

闭环的派发需要「一轮一会话」：干活的上下文用完即弃，主会话只留薄薄的 tick 记录。可用两座桥：①workflow 子代理（活在宿主对话里，用统一号池等已验证模型，已跑通三轮）；②spawn 无头 zcode CLI 会话（`node <zcode.cjs> -p "<指令>" --cwd <项目根> --surface terminal`，独立于任何对话，CLI v0.17.0 支持 -p/--cwd/--mode/--surface）。桥②当前被 CLI 自身模型凭据 401 阻塞：桌面端的模型池配置存于应用内部存储，CLI 读不到（已验证：供应商名只出现在会话产物中，无任何 CLI 可读的静态配置），机器上也没有第二个能跑的无头 CLI。CLI 需要用户执行一次 `zcode login` 浏览器授权。

## 决定

双桥并存：心跳派发时优先桥②（spawn CLI 会话，独立于宿主对话），CLI 不可用（未登录/401）时回退桥①（workflow 子代理，可指定统一号池模型）。两座桥共用同一账本与门禁：新会话只读 .pm/ 账本恢复状态（get_status + 卡上的 steps/checkpoint），不继承任何对话历史；一轮一会话，干活的上下文用完即弃。权限模式默认 yolo（-p 的默认值）；如需危险命令暂停改用 --mode guarded，但无人值守下会停等人。pm-mcp 本身仍不调用模型：spawn CLI 的是心跳（一个模型会话），被 spawn 的会话烧的是用户自己配置的模型额度。

## 后果

1) ADR-008 的「pm-mcp 不唤起会话」边界收窄为「pm-mcp 不唤起会话；心跳（模型侧）可以 spawn CLI 会话」——pm-mcp 仍然零 Key。2) 代价：桥②的模型是 CLI 自己配置的（login 后的 bigmodel 计划），无法按轮指定统一号池模型（CLI 无 --model 参数）；按轮指定模型只有桥①支持。3) 无人值守下 -p 默认 yolo，spawn 出的会话拥有完整工具权限，靠门禁与复核兜底。4) CLI 登录后需重跑探针验证（get_orchestrator 可读、能退出），再切换派发。
